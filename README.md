# Лабораторная работа №3 (NoSQL): wide-column хранилище Apache Cassandra

**Вариант 8888.** Продолжение лабораторных №1 (Redis) и №2 (MongoDB, вариант 673): бронирование аудиторий.
CRUD API и прежние хранилища работают как раньше. В новую систему, кластер Apache Cassandra 5.0,
пишется **история изменения основных объектов**.

| Параметр варианта | Как сделано |
|---|---|
| хранимые события | история изменений брони, помещения, категории, пользователя, организации (16 типов событий) |

## 2. Кластер

`docker-compose.yml` поднимает три узла: `cassandra-1..3`, один DC `dc1`, стойки `rack1..3`,
`GossipingPropertyFileSnitch`, по 16 vnode на узел. Keyspace создаётся приложением при подключении:

```sql
CREATE KEYSPACE booking_events WITH replication = {'class': 'NetworkTopologyStrategy', 'dc1': 3};
```

```
--  Address      Load       Tokens  Owns  Host ID                               Rack
UN  172.30.0.13  41.29 MiB  16      ?     15c5b82b-561a-4827-9725-af8ff572137c  rack3
UN  172.30.0.12  50.7 MiB   16      ?     4aa8b4ac-af78-4a80-8721-222ed52ceb01  rack2
UN  172.30.0.11  50.51 MiB  16      ?     5b743417-e612-4b18-a1eb-082b2b9e56c5  rack1
```

Особенности стенда:

- **Приложение работает на хосте, а не в docker-сети.** Каждый узел слушает CQL на своём порту
  (9042/9043/9044) и объявляет клиентам `broadcast_rpc_address = 127.0.0.1`. Драйвер узнаёт порты узлов
  из `system.peers_v2` и подключается к каждому напрямую. Межузловой трафик (gossip, репликация,
  hints) идёт по внутренней docker-сети.
- **Адреса узлов статические** (172.30.0.11–13). Без этого после рестарта контейнеры получали IP
  вперемешку, и gossip какое-то время видел чужие host id на старых адресах.
- Узлы стартуют строго по одному (`depends_on: service_healthy`): Cassandra не допускает
  одновременного bootstrap нескольких узлов.
- Guardrail `partition_size_warn_threshold` снижен до 10 MiB, чтобы в эксперименте с крупными
  партициями появлялись предупреждения. По умолчанию он выключен.
- Cassandra здесь дополнительное хранилище. Если кластер недоступен при старте, приложение всё равно
  запускается и раз в 10 с пробует подключиться снова (`CassandraConnector`).

## 3. Модель данных: таблицы от запросов

Каждая таблица обслуживает ровно один запрос и читается только по полному partition key с диапазоном
по clustering column. Поэтому не нужны ни `ALLOW FILTERING`, ни вторичные индексы (п. 5 задания).
Схема описана в `cassandra/CassandraSchema.java`.

| Запрос | Таблица | Partition key | Clustering columns |
|---|---|---|---|
| **Q1 (обязательный)**: события типа за период | `events_by_type` | `(event_type, bucket)` | `occurred_at DESC, event_id DESC` |
| Q2: история одного объекта | `events_by_entity` | `(entity_type, entity_id)` | `occurred_at DESC, event_id DESC` |
| Q3: действия пользователя за период | `events_by_actor` | `(actor_id, bucket)` | `occurred_at DESC, event_id DESC` |
| служебная: каталог бакетов потока | `event_buckets` | `(stream)` | `bucket DESC` |
| эксперимент: Q1 без бакета | `events_by_type_unbucketed` | `(event_type)` | `occurred_at DESC, event_id DESC` |

```sql
CREATE TABLE events_by_type (
    event_type text, bucket int, occurred_at timestamp, event_id timeuuid,
    seq bigint, entity_type text, entity_id text, actor_id text, summary text, payload text,
    PRIMARY KEY ((event_type, bucket), occurred_at, event_id)
) WITH CLUSTERING ORDER BY (occurred_at DESC, event_id DESC);
```

**Обоснование ключей.**

- `event_type` в partition key: обязательный запрос всегда задаёт тип, поэтому весь ответ лежит в
  партициях одного типа.
- Тип сам по себе — плохой partition key. Типов всего 16, поток каждого бесконечен и сильно
  неравномерен (`BOOKING_SUBMITTED` встречается в сотни раз чаще, чем `CATEGORY_DELETED`), то есть
  партиция росла бы без ограничений. Поэтому добавлен `bucket`: каждые 100 000 событий типа начинают
  новую партицию (раздел 7 показывает, что будет без него).
- `occurred_at` — первая clustering column. Период выбирается диапазоном по ней внутри партиции
  (`occurred_at >= ? AND occurred_at <= ?`), без сканирования. Порядок `DESC` соответствует
  типичному запросу «сначала новые»; для `order=asc` Cassandra читает партицию в обратном порядке.
- `event_id timeuuid` делает ключ уникальным, если два события пришли в одну миллисекунду.
  Он же служит идентификатором события при повторной записи (идемпотентность).
- `events_by_entity` без бакета: история одного объекта ограничена его жизненным циклом
  (у брони 2–10 событий), поэтому партиция естественно маленькая.
- `events_by_actor` с бакетом: администратор может обработать неограниченно много заявок, и его
  поток растёт так же, как поток типа.
- Значения хранятся в каждой таблице целиком (денормализация). Чтение по любому из трёх запросов
  обходится одним обращением, без join на стороне приложения.

### Бакетирование по 100 000 событий

Бакет по варианту задаётся числом событий, а не интервалом времени. Значит, нужен монотонный номер
события в потоке. Потоки: `type:<ТИП>` и `actor:<id>`.

1. **Счётчик** — `INCR events:seq:<поток>` в Redis (хранилище из лабы 1; атомарно и без LWT в Cassandra).
   Тогда `bucket = (seq − 1) / 100 000`.
2. **Каталог.** Первое событие бакета (`seq mod 100 000 = 1`) добавляет строку
   `(stream, bucket, first_event_at)` в `event_buckets`. Каталог крошечный: одна строка на 100 000 событий.
3. **Чтение Q1/Q3.** Из каталога берутся бакеты, которые пересекаются с периодом: бакет `i` покрывает
   `[first_i, first_{i+1})`. Затем они читаются по очереди (новые первыми при `desc`), каждый —
   запросом по полному partition key.
4. **Устойчивость.**
   - Строка каталога пишется `USING TIMESTAMP (MAX − время события)`, поэтому при повторной записи
     побеждает самое раннее `first_event_at`, и запись идемпотентна.
   - Если Redis потерял ключ (INCR вернул 1, а в каталоге бакеты уже есть), счётчик переводится на
     начало следующего бакета, чтобы не дописывать в старые партиции.
   - Если Redis недоступен, событие пишется в последний известный бакет. Бакет может немного
     превысить 100 000, но событие не теряется.

### Пагинация

Пагинация курсорная, без OFFSET. `nextPageToken` — это base64url от `бакет:paging state драйвера`.
Страница может начаться в середине одного бакета и закончиться в следующем. Глубокая страница стоит
столько же, сколько первая: Cassandra продолжает чтение с сохранённой позиции. В ответе также
указаны прочитанные бакеты, уровень согласованности, координатор и время выполнения:

```json
{"items":[{"eventId":"…","occurredAt":"2026-11-08T10:41:03.512+03:00","eventType":"BOOKING_APPROVED",
  "entityType":"BOOKING","entityId":"…","actorId":"100000","summary":"заявка одобрена",
  "payload":{"from":"UNDER_REVIEW","to":"APPROVED","reason":"Аудитория свободна"},"bucket":0,"seq":12}],
 "size":1,"nextPageToken":"MDpBQUFB…","bucketsScanned":[0],"consistency":"LOCAL_QUORUM",
 "coordinator":"/127.0.0.1:9043","tookMs":4.1}
```

## 4. Запись событий

Сервисы лаб 1–2 после каждого изменения вызывают `EventRecorder.record(...)`. Это `BookingService`
(создание, отправка, одобрение и отклонение, удаление, комментарии; заявки из корзины тоже
проходят через `createBooking`), а также `RoomService`, `CategoryService`, `PersonService` и
`OrganizationService` (для организации хранятся значения до и после изменения).

- **Только после коммита MongoDB.** Событие регистрируется как `afterCommit` текущей транзакции,
  поэтому откатившиеся изменения в истории не появляются.
- **Асинхронно.** CRUD не ждёт Cassandra, её задержка и доступность не влияют на API первых лаб
  (в разделе 6 CRUD отвечает 201 при потерянном кворуме).
- **Одним LOGGED batch в три таблицы**, плюс строки каталога. Batchlog гарантирует, что три
  представления события не разойдутся, даже если координатор упадёт посередине записи.
  Цена — дополнительная запись batchlog на два других узла (это проявилось в разделе 6).
- **Очередь повторной отправки.** При ошибке (нет кворума, таймаут) событие остаётся в памяти и
  дописывается раз в 5 с, когда кластер снова доступен. Запись идемпотентна (тот же `event_id`),
  поэтому повтор не создаёт дублей.
- Уровень согласованности по умолчанию — `LOCAL_QUORUM` для записи и чтения. Так как
  W + R = 2 + 2 > RF = 3, чтение всегда видит подтверждённую запись.

## 5. API

| Метод | Описание | Доступ |
|---|---|---|
| `GET /api/events/by-type?type&from&to&order&size&pageToken&consistency` | **Q1**: события типа за период | админ |
| `GET /api/events/by-entity/{BOOKING\|ROOM\|…}/{id}?…` | Q2: история объекта | своя бронь и свой профиль — владелец, остальное — админ |
| `GET /api/events/by-actor/{personId}?from&to&…` | Q3: действия пользователя | сам пользователь или админ |
| `GET /api/events/types` | список типов событий | все |
| `GET /api/admin/cassandra/status` | узлы, их состояние, репликация, очередь записи | админ |
| `GET /api/admin/cassandra/buckets?stream=type:BOOKING_CREATED` | каталог бакетов | админ |
| `POST /api/admin/cassandra/experiments/consistency?levels=ONE,ALL&ops=300&mode=batch\|single` | эксперимент согласованности | админ |
| `POST /api/admin/cassandra/experiments/load?kind=write\|read\|mixed&ops&concurrency&consistency` | нагрузка | админ |
| `POST /api/admin/cassandra/experiments/hot-partition/{fill,reset}`, `GET …/report` | hot partition; reset удаляет данные и `hot_partition_lab`, а нумерация событий продолжается: каталог бакетов записан с обратным timestamp и обычным DELETE не удаляется | админ |

`from` и `to` принимают дату (`2026-11-08`), локальное время (`2026-11-08T10:00`) или время с зоной.
Ошибки Cassandra (нет кворума, таймаут реплик) возвращаются как HTTP 503 с именем исключения драйвера.
Служебные эндпоинты `/api/admin/cassandra/**` исключены из лимита 60 запросов в минуту из лабы 1,
потому что сами генерируют нагрузку.

## 6. Эксперимент: согласованность ONE против ALL

`scripts/exp_consistency.sh`. Для каждого уровня выполняется 300 пар «записать событие реальным
путём приложения (LOGGED batch) → прочитать его точечным запросом». Уровни чередуются на каждой
итерации, чтобы фоновые эффекты (GC, компакция) влияли на оба одинаково. Задержки в мс.

| Стадия | CL | запись ok % | запись avg / p95 | чтение ok % | чтение avg / p95 | ошибки |
|---|---|---|---|---|---|---|
| A. все узлы здоровы | ONE | 100 | 4.6 / 6.1 | 100 | 3.0 / 4.2 | — |
| | ALL | 100 | 5.5 / 7.3 | 100 | 4.1 / 5.2 | — |
| B. cassandra-3 ограничен 0.3 CPU | ONE | 100 | 67.8 / 190.3 | 100 | 31.5 / 179.9 | — |
| | ALL | 100 | **112.0 / 301.0** | 100 | 53.9 / 184.7 | — |
| C. cassandra-3 заморожен (`docker pause`) | ONE | 99.3 | 3.8 / 5.4 | 100 | 3.2 / 4.8 | 2 × WriteTimeout |
| | ALL | **0** | — | **0** | — | 297 × Unavailable, 2 × WriteTimeout |
| D. cassandra-3 остановлен | ONE | 100 | 3.8 / 5.6 | 100 | 3.3 / 4.6 | — |
| | ALL | **0** | — | **0** | — | 300 × Unavailable |

Медленную реплику пришлось моделировать нехваткой CPU: модуля `netem` (`tc qdisc … netem delay`)
в ядре WSL2 нет.

**Выводы.**

- **Задержка.** ALL ждёт ответа от всех трёх реплик, поэтому его задержка равна задержке самой
  медленной. На здоровом кластере разница небольшая (+20–40 %). Но достаточно одного
  перегруженного узла, и запись с ALL становится в 1,6 раза медленнее, чем с ONE (p95 301 мс
  против 190 мс). ONE тоже замедлился, потому что перегруженный узел остаётся координатором
  части запросов.
- **Доступность.** ALL недоступен, как только недоступна хотя бы одна реплика, тогда как ONE
  продолжает работать.
- **Зависшая реплика хуже выключенной.** Пока драйвер и gossip не признали узел мёртвым, запросы
  ждут таймаута (WriteTimeout через 2 с, DriverTimeout через 5 с). После этого координатор сразу
  отвечает `UnavailableException`: проверка числа живых реплик делается до отправки запроса.
- **Read-your-writes.** На стадии B чтение с ONE сразу после записи с ONE **не нашло только что
  записанное событие в 10 случаях из 300**. Запись подтвердила одна быстрая реплика, а чтение попало
  на перегруженный cassandra-3, который мутацию ещё не применил. С ALL такого не было ни разу
  (300 из 300). Это прямое следствие условия W + R > RF: для ONE + ONE получается 2 ≤ 3, гарантии
  нет. Для ALL + ALL получается 6 > 3. На здоровом кластере (A, D) пропусков не было: реплики
  успевают применить запись. Поэтому в приложении по умолчанию используется `LOCAL_QUORUM`
  (2 + 2 > 3).

## 7. Эксперимент с отказом: потеря доступного кворума

`scripts/exp_quorum_loss.sh`. RF = 3, кворум = 2 реплики. Вывод консоли — `results/quorum_console.txt`.

| Стадия | живых узлов | ONE запись / чтение | QUORUM | ALL |
|---|---|---|---|---|
| A. все узлы | 3 | ✔ / ✔ | ✔ | ✔ |
| B. остановлен cassandra-3 | 2 | ✔ / ✔ | ✔ (2 из 3) | ✘ Unavailable |
| C. остановлен ещё cassandra-2 | 1 | **✘ batch** / ✔ | ✘ кворум потерян | ✘ |
| C, одиночная вставка вместо batch | 1 | ✔ / ✔ | ✘ | — |
| D. узлы вернулись | 3 | ✔ / ✔ | ✔ | ✔ |

Что происходило на стадии C:

- **CRUD лабораторных 1–2 работает.** Создание организаций в MongoDB вернуло `201 201 201`.
- **События не теряются.** Запись с `LOCAL_QUORUM` невозможна, и события копятся в очереди повторной
  отправки (`pendingRetry: 3`).
- **Обязательный запрос с QUORUM** вернул HTTP 503 (`UnavailableException: 2 required but only 1 alive`).
- **Тот же запрос с ONE** вернул 200, но без трёх новых событий: они ещё в очереди. Это наглядная
  «несогласованная» картина: доступность ценой актуальности.
- **Неожиданный результат: LOGGED batch не проходит даже с ONE.** Ошибка
  `Not enough replicas available for query at consistency TWO (2 required but only 0 alive)`.
  Перед применением батча координатор пишет batchlog на два других узла с CL TWO, а их нет.
  Одиночная вставка с ONE проходит.
- **Hints.** Для обоих лежащих узлов на cassandra-1 появились файлы hints
  (`<host id получателя>-….hints`, до 48 КБ). По имени файла видно, кому они предназначены.

После возврата узлов (стадия D) очередь приложения дописана (`pendingRetry: 0`), обязательный запрос
с QUORUM находит все 3 события, а hints доставлены и удалены (`no hint files`). Hints хранятся
не дольше `max_hint_window = 3h`. Если узел пролежал дольше, данные выравнивает только
`nodetool repair`.

**Вывод.** При RF = 3 кластер переживает потерю одного узла без потери кворума. При потере двух
кластер остаётся доступен только на уровне ONE, причём не для LOGGED batch. Приложение сохраняет
работоспособность CRUD за счёт асинхронной записи с очередью, а история изменений догоняет состояние
после восстановления кворума.

## 8. Механизм: размер partition и hot partition

`scripts/exp_hot_partition.sh`. Записано 300 000 событий одного типа одновременно в четыре таблицы:

- `events_by_type` — с бакетом, в keyspace приложения (RF = 3);
- `events_by_type_unbucketed` — без бакета, в keyspace приложения (RF = 3);
- те же две таблицы в отдельном keyspace `hot_partition_lab` с RF = 1, чтобы было видно, на каком
  узле лежит каждая партиция.

Размер одного события около 300 байт.

**Размер партиций** (`nodetool tablestats` и `tablehistograms`, cassandra-1):

| | партиций | строк в партиции | макс. размер партиции | COUNT по партиции |
|---|---|---|---|---|
| с бакетом (100 000) | 3 | 100 000 | **30.1 МБ** | 1.0–1.5 с |
| без бакета | 1 | 300 000 | **90.0 МБ** | 4.0 с |

- Без бакета партиция растёт линейно и бесконечно. При 1 млн событий это уже ~300 МБ, больше
  общепринятого предела в ~100 МБ. С бакетом размер ограничен сверху: ~30 МБ при любом объёме потока.
- Guardrail сработал на обоих вариантах (порог снижен до 10 MiB):
  `Guardrail partition_size violated: Partition booking_events.events_by_type_unbucketed:HOT_PARTITION_DEMO … has size 82255034`.
- Одиночный `COUNT(*)` по партиции на 300 000 строк не уложился в серверный `read_request_timeout = 5 s`
  (`ReadTimeoutException`). Подсчёт пришлось сделать постраничным. Это типичный симптом большой
  партиции: её нельзя прочитать целиком одним запросом. То же касается компакции, repair и
  стриминга при добавлении узла, которые работают с партицией как с единым целым.

**Hot partition — распределение по узлам** (keyspace с RF = 1, `nodetool tablestats` на каждом узле):

| | cassandra-1 | cassandra-2 | cassandra-3 |
|---|---|---|---|
| без бакета: `Local write count` | **300 000** | 0 | 0 |
| с бакетом: `Local write count` | 0 | 300 000 | 0 |
| с бакетом: куда лягут бакеты 0–29 (по token map) | 5 | 11 | 14 |

- **Партиция целиком живёт на одних и тех же репликах.** Без бакета весь поток типа навсегда
  закреплён за одним узлом (при RF = 3 — за одними и теми же тремя репликами), и остальные узлы ему
  не помогают.
- **Бакеты распределяют поток во времени.** Каждый следующий бакет — новый токен на кольце, поэтому
  со временем поток расходится по всем узлам: бакеты 0–29 распределились как 5 / 11 / 14.
  Три записанных бакета случайно попали на один узел (вероятность 1/9), что и показывает, что
  бакетов должно быть много.
- **Но бакет по счётчику не снимает «горячесть» записи.** `nodetool toppartitions` во время записи
  показал для обеих таблиц одну горячую партицию:
  `HOT_PARTITION_DEMO` (без бакета) и `HOT_PARTITION_DEMO:0` (с бакетом), около 40 000 записей
  за 20 с каждая. В любой момент вся запись типа идёт в текущий бакет. Бакетирование ограничивает
  размер партиции, но не распределяет одновременную нагрузку. Если тип настолько популярен, что
  одна партиция не выдерживает поток записи, нужен дополнительный шард в partition key:
  `(event_type, bucket, shard)`, где `shard = hash(event_id) mod N`. Чтение тогда опрашивает N партиций.
- **При RF = 3 на 3 узлах** каждая партиция хранится на всех узлах. Перекоса нагрузки между узлами
  в основном keyspace нет, и hot partition проявляется только как рост одной партиции. На кластере
  из 6+ узлов тот же поток нагружал бы 3 узла из 6.

**Задержка типовых чтений** (CL ONE, 30 повторов, страница 100 строк), avg / p95 в мс:

| запрос | с бакетом | без бакета |
|---|---|---|
| 100 самых новых | 7.6 / 9.3 | 7.6 / 9.3 |
| 100 самых старых | 7.5 / 9.9 | 11.6 / **36.5** |
| 100 из середины периода | 5.8 / 8.2 | 5.9 / 7.6 |

Чтение начала партиции не зависит от её размера: Cassandra находит нужную строку по индексу
clustering columns. Хвост большой партиции читается заметно медленнее (p95 в 3,7 раза выше).
Главная цена большой партиции не в задержке типовых запросов, а в операциях над партицией целиком
(COUNT, компакция, repair) и в закреплении нагрузки за одними и теми же узлами.

## 9. Нагрузочный эксперимент

`scripts/exp_load.sh`. По 20 000 операций, асинхронно, задано число запросов «в полёте».

- Запись — реальный путь приложения: LOGGED batch в три таблицы.
- Чтение — обязательный запрос: страница из 50 событий типа за случайный период.
- Mixed — 50 % записей и 50 % чтений.

Все три узла, приложение и клиент работают на одном ноутбуке (16 ядер, WSL2, 7 ГБ под Docker),
поэтому абсолютные цифры отражают стенд, а не Cassandra.

**Основной профиль** (LOCAL_QUORUM, 64 в полёте):

| нагрузка | throughput, оп/с | avg, мс | p95, мс | p99, мс | успешно |
|---|---|---|---|---|---|
| запись | 1 535 | 41.2 | 87.7 | 140.2 | 100 % |
| чтение Q1 | 1 552 | 40.9 | 78.2 | 126.4 | 100 % |
| смешанная: запись | 1 683 | 43.9 | 74.0 | 128.1 | 100 % |
| смешанная: чтение | 1 683 | 31.5 | 57.1 | 95.2 | 100 % |

**Параллелизм** (запись, LOCAL_QUORUM):

| в полёте | 1 | 8 | 32 | 128 | 256 |
|---|---|---|---|---|---|
| throughput, оп/с | 156 | 677 | 1 019 | 1 241 | 2 472 |
| avg, мс | 6.3 | 11.7 | 31.1 | 77.8 | 100.0 |
| p95, мс | 8.9 | 19.9 | 54.3 | 131.9 | 171.0 |

**Уровень согласованности** (смешанная, 64 в полёте):

| CL | throughput, оп/с | запись avg / p95 | чтение avg / p95 |
|---|---|---|---|
| ONE | 1 883 | 46.8 / 94.5 | **20.0 / 43.4** |
| LOCAL_QUORUM | 1 680 | 45.0 / 79.6 | 30.6 / 57.3 |
| ALL | 1 465 | 52.3 / 88.5 | 34.4 / 62.4 |

**Выводы.**

- Пока стенд не насыщен, throughput растёт с параллелизмом почти линейно (1 → 8 в полёте даёт
  ×4,3), а задержка почти не растёт.
- Дальше растёт в основном задержка (закон Литтла: среднее число запросов «в полёте» равно
  throughput × задержка). Насыщение наступает примерно при 32 запросах «в полёте».
- Уровень согласованности сильнее всего влияет на чтение. Для чтения с ONE достаточно одной
  реплики, поэтому оно в 1,5 раза быстрее, чем с кворумом. На запись CL влияет меньше: при любом CL
  мутация уходит на все три реплики, а CL определяет только число ожидаемых подтверждений.
  ALL снижает throughput на 13 % относительно LOCAL_QUORUM.
- В соседних запусках при насыщении наблюдались единичные WriteTimeout (0,4 % при 128 в полёте,
  0,2 % при массовой записи в эксперименте hot partition). Это перегрузка узлов, а не ошибка
  приложения. Повторная отправка в приложении такие события дописывает.
- Разброс между повторными запусками при высокой нагрузке достигает десятков процентов
  (компакция, GC, фоновые процессы ноутбука). Например, первый прогон, сразу после записи
  300 000 строк, дал 491 оп/с на запись из-за идущей компакции. Сравнивать корректно только
  результаты одного прогона.

## 10. Telegram-бот (`lab3-nosql-tg`)

Бот обращается только к HTTP API бэкенда. Новые команды:

| Команда | Запрос |
|---|---|
| `/history <id>` и кнопка «История изменений» в карточке заявки | Q2: история заявки |
| `/myactions` | Q3: журнал своих действий |
| `/events <ТИП> [с] [по]` (админ) | **Q1**: события типа за период, например `/events BOOKING_APPROVED 2026-11-01 2026-11-30` |
| `/eventtypes` (админ) | список типов с кнопками запроса |
| `/more` и кнопка «Ещё 10» | следующая страница последнего запроса |

Курсор страницы хранится в контексте чата: в callback-кнопку Telegram (не больше 64 байт) он не
помещается. Запросы бота проверяются тестом `BackendEventsIT` на живом бэкенде:
`BACKEND_IT=1 ./gradlew test`.
