## 2. Кластер

`docker-compose.yml` поднимает три узла: `cassandra-1..3`, один DC `dc1`, стойки `rack1..3`,
`GossipingPropertyFileSnitch`, по 16 vnode на узел. Keyspace создаётся приложением при подключении:

```sql
CREATE KEYSPACE booking_events WITH replication = {'class': 'NetworkTopologyStrategy', 'dc1': 3};
```

```

UN  172.30.0.13  41.29 MiB  16      ?     15c5b82b-561a-4827-9725-af8ff572137c  rack3
UN  172.30.0.12  50.7 MiB   16      ?     4aa8b4ac-af78-4a80-8721-222ed52ceb01  rack2
UN  172.30.0.11  50.51 MiB  16      ?     5b743417-e612-4b18-a1eb-082b2b9e56c5  rack1
```

Особенности стенда:

- **Приложение работает на хосте, а не в docker-сети.** Каждый узел слушает CQL на своём порту
  (9042/9043/9044) и объявляет клиентам `broadcast_rpc_address = 127.0.0.1`. Драйвер узнаёт порты узлов
  из `system.peers_v2` и подключается к каждому напрямую. Межузловой трафик (gossip, репликация,
  hints) идёт по внутренней docker-сети.
- **Адреса узлов статические** (172.30.0.11–13). Без этого после рестарта контейнеры получали IP
  вперемешку, и gossip какое-то время видел чужие host id на старых адресах.
- Узлы стартуют строго по одному (`depends_on: service_healthy`): Cassandra не допускает
  одновременного bootstrap нескольких узлов.
- Guardrail `partition_size_warn_threshold` снижен до 10 MiB, чтобы в эксперименте с крупными
  партициями появлялись предупреждения. По умолчанию он выключен.
- Cassandra здесь дополнительное хранилище. Если кластер недоступен при старте, приложение всё равно
  запускается и раз в 10 с пробует подключиться снова (`CassandraConnector`).

## 3. Модель данных: таблицы от запросов

Каждая таблица обслуживает ровно один запрос и читается только по полному partition key с диапазоном
по clustering column. Поэтому не нужны ни `ALLOW FILTERING`, ни вторичные индексы (п. 5 задания).
Схема описана в `cassandra/CassandraSchema.java`.

| Запрос | Таблица | Partition key | Clustering columns |
|---|---|---|---|
| **Q1 (обязательный)**: события типа за период | `events_by_type` | `(event_type, bucket)` | `occurred_at DESC, event_id DESC` |
| Q2: история одного объекта | `events_by_entity` | `(entity_type, entity_id)` | `occurred_at DESC, event_id DESC` |
| Q3: действия пользователя за период | `events_by_actor` | `(actor_id, bucket)` | `occurred_at DESC, event_id DESC` |
| служебная: каталог бакетов потока | `event_buckets` | `(stream)` | `bucket DESC` |
| эксперимент: Q1 без бакета | `events_by_type_unbucketed` | `(event_type)` | `occurred_at DESC, event_id DESC` |

```sql
CREATE TABLE events_by_type (
    event_type text, bucket int, occurred_at timestamp, event_id timeuuid,
    seq bigint, entity_type text, entity_id text, actor_id text, summary text, payload text,
    PRIMARY KEY ((event_type, bucket), occurred_at, event_id)
) WITH CLUSTERING ORDER BY (occurred_at DESC, event_id DESC);
```

**Обоснование ключей.**

- `event_type` в partition key: обязательный запрос всегда задаёт тип, поэтому весь ответ лежит в
  партициях одного типа.
- Тип сам по себе — плохой partition key. Типов всего 16, поток каждого бесконечен и сильно
  неравномерен (`BOOKING_SUBMITTED` встречается в сотни раз чаще, чем `CATEGORY_DELETED`), то есть
  партиция росла бы без ограничений. Поэтому добавлен `bucket`: каждые 100 000 событий типа начинают
  новую партицию (раздел 7 показывает, что будет без него).
- `occurred_at` — первая clustering column. Период выбирается диапазоном по ней внутри партиции
  (`occurred_at >= ? AND occurred_at <= ?`), без сканирования. Порядок `DESC` соответствует
  типичному запросу «сначала новые»; для `order=asc` Cassandra читает партицию в обратном порядке.
- `event_id timeuuid` делает ключ уникальным, если два события пришли в одну миллисекунду.
  Он же служит идентификатором события при повторной записи (идемпотентность).
- `events_by_entity` без бакета: история одного объекта ограничена его жизненным циклом
  (у брони 2–10 событий), поэтому партиция естественно маленькая.
- `events_by_actor` с бакетом: администратор может обработать неограниченно много заявок, и его
  поток растёт так же, как поток типа.
- Значения хранятся в каждой таблице целиком (денормализация). Чтение не требует join. Q1 и Q3 могут обращаться к нескольким бакетам.

### Бакетирование по 100 000 событий

Бакет по варианту задаётся числом событий, а не интервалом времени. Значит, нужен монотонный номер
события в потоке. Потоки: `type:<ТИП>` и `actor:<id>`.

1. **Счётчик** — `INCR events:seq:<поток>` в Redis (хранилище из лабы 1; атомарно и без LWT в Cassandra).
   Тогда `bucket = (seq − 1) / 100 000`.
2. **Каталог.** Первое событие бакета (`seq mod 100 000 = 1`) добавляет строку
   `(stream, bucket, first_event_at)` в `event_buckets`. Каталог крошечный: одна строка на 100 000 событий.
3. **Чтение Q1/Q3.** Все бакеты потока читаются по полному partition key с диапазоном времени.
   Ограниченные префиксы объединяются по времени и timeuuid, поскольку диапазоны бакетов могут пересекаться.
4. **Устойчивость.**
   - Строка каталога пишется `USING TIMESTAMP (MAX − время события)`, поэтому при повторной записи
     побеждает самое раннее `first_event_at`, и запись идемпотентна.
   - Если Redis потерял ключ (INCR вернул 1, а в каталоге бакеты уже есть), счётчик переводится на
     начало следующего бакета, чтобы не дописывать в старые партиции.
   - Если Redis недоступен, подготовка откладывается в очередь памяти, запись без номера запрещена.

### Пагинация

Пагинация курсорная, без OFFSET. Для Q1/Q3 курсор содержит последнюю пару (время, timeuuid).
Каждая страница объединяет ограниченные префиксы всех бакетов, поэтому её стоимость зависит от их числа.
Для Q2 сохраняется paging state драйвера. В ответе также
указаны прочитанные бакеты, уровень согласованности, координатор и время выполнения:

```json
{"items":[{"eventId":"…","occurredAt":"2026-11-08T10:41:03.512+03:00","eventType":"BOOKING_APPROVED",
  "entityType":"BOOKING","entityId":"…","actorId":"100000","summary":"заявка одобрена",
  "payload":{"from":"UNDER_REVIEW","to":"APPROVED","reason":"Аудитория свободна"},"bucket":0,"seq":12}],
 "size":1,"nextPageToken":"MDpBQUFB…","bucketsScanned":[0],"consistency":"LOCAL_QUORUM",
 "coordinator":"/127.0.0.1:9043","tookMs":4.1}
```

## 4. Запись событий

Сервисы лаб 1–2 после каждого изменения вызывают `EventRecorder.record(...)`. Это `BookingService`
(создание, отправка, одобрение и отклонение, удаление, комментарии; заявки из корзины тоже
проходят через `createBooking`), а также `RoomService`, `CategoryService`, `PersonService` и
`OrganizationService` (для организации хранятся значения до и после изменения).

- **Только после коммита MongoDB.** Событие регистрируется как `afterCommit` текущей транзакции,
  поэтому откатившиеся изменения в истории не появляются.
- **Асинхронно.** CRUD не ждёт Cassandra, её задержка и доступность не влияют на API первых лаб
  (в разделе 6 CRUD отвечает 201 при потерянном кворуме).
- **Одним LOGGED batch в три таблицы**, плюс строки каталога. Batchlog гарантирует, что три
  представления события не разойдутся, даже если координатор упадёт посередине записи.
  Цена — дополнительная запись batchlog на два других узла (это проявилось в разделе 6).
- **Очередь повторной отправки.** При ошибке (нет кворума, таймаут) событие остаётся в памяти и
  дописывается раз в 5 с, когда кластер снова доступен. Запись идемпотентна (тот же `event_id`),
  поэтому повтор не создаёт дублей.
- Уровень согласованности по умолчанию — `LOCAL_QUORUM` для записи и чтения. Так как
  W + R = 2 + 2 > RF = 3, чтение всегда видит подтверждённую запись.

## 5. API

| Метод | Описание | Доступ |
|---|---|---|
| `GET /api/events/by-type?type&from&to&order&size&pageToken&consistency` | **Q1**: события типа за период | админ |
| `GET /api/events/by-entity/{BOOKING\|ROOM\|…}/{id}?…` | Q2: история объекта | своя бронь и свой профиль — владелец, остальное — админ |
| `GET /api/events/by-actor/{personId}?from&to&…` | Q3: действия пользователя | сам пользователь или админ |
| `GET /api/events/types` | список типов событий | все |
| `GET /api/admin/cassandra/status` | узлы, их состояние, репликация, очередь записи | админ |
| `GET /api/admin/cassandra/buckets?stream=type:BOOKING_CREATED` | каталог бакетов | админ |
| `POST /api/admin/cassandra/experiments/consistency?levels=ONE,ALL&ops=300&mode=batch\|single` | эксперимент согласованности | админ |
| `POST /api/admin/cassandra/experiments/load?kind=write\|read\|mixed&ops&concurrency&consistency` | нагрузка | админ |
| `POST /api/admin/cassandra/experiments/hot-partition/{fill,reset}`, `GET …/report` | hot partition; reset удаляет данные и `hot_partition_lab`, а нумерация событий продолжается: каталог бакетов записан с обратным timestamp и обычным DELETE не удаляется | админ |

`from` и `to` принимают дату (`2026-11-08`), локальное время (`2026-11-08T10:00`) или время с зоной.
Ошибки Cassandra (нет кворума, таймаут реплик) возвращаются как HTTP 503 с именем исключения драйвера.
Служебные эндпоинты `/api/admin/cassandra/**` исключены из лимита 60 запросов в минуту из лабы 1,
потому что сами генерируют нагрузку.

Повторный прогон выполнен **18 ноября 2026** после исправлений. Все сквозные проверки прошли;
HTTP-пагинация через границу бакетов проверена на 82 событиях. Полный отчёт:
[results/RERUN_REPORT.md](results/RERUN_REPORT.md). Старые результаты сохранены отдельно в
`results/archive_before_rerun_2026-11-18/`. Финальное состояние: три узла UP, очередь пуста,
отброшенных событий нет. Параметры стенда: 16 CPU, около 15.4 GiB памяти Docker, Cassandra 5.0.9.

## 9. Нагрузка

По 20000 операций, прогрев 5000 записей. Throughput — число всех операций профиля за время профиля; в смешанном профиле одно и то же общее значение показано у записи и чтения и не складывается. ## 10. Telegram-бот (`lab3-nosql-tgbot`)

Бот обращается только к HTTP API бэкенда. Новые команды:

| Команда | Запрос |
|---|---|
| `/history <id>` и кнопка «История изменений» в карточке заявки | Q2: история заявки |
| `/myactions` | Q3: журнал своих действий |
| `/events <ТИП> [с] [по]` (админ) | **Q1**: события типа за период, например `/events BOOKING_APPROVED 2026-11-01 2026-11-30` |
| `/eventtypes` (админ) | список типов с кнопками запроса |
| `/more` и кнопка «Ещё 10» | следующая страница последнего запроса |

Курсор страницы хранится в контексте чата: в callback-кнопку Telegram (не больше 64 байт) он не
помещается. Запросы бота проверяются тестом `BackendEventsIT` на живом бэкенде:
`BACKEND_IT=1 ./gradlew test`.

## Исправления после проверки

- При недоступном Redis выделение номера откладывается; события ждут подготовки в очереди памяти.
  Запись в последний бакет без счётчика запрещена. Инициализация и INCRBY атомарны (Lua).
- Q1/Q3 перечисляют все бакеты из каталога, читают ограниченный префикс каждого и объединяют
  результаты по (occurred_at, event_id). Пересечение временных диапазонов бакетов поддерживается.
  Цена страницы зависит от количества бакетов. Курсор Q1/Q3 теперь содержит последнюю пару
  (время, идентификатор); старые курсоры после обновления нужно сбросить. Snapshot не гарантируется:
  поздно доставленные события перед курсором видны при новом запросе.
- Удаления помещений, категорий и пользователей записываются после успешного deleteById.
- Задержки успешных операций возвращаются как null при отсутствии успешных измерений.
  failureAvgMs и failureP95Ms отдельно измеряют время до ошибки. Результаты повторного прогона содержат новые поля;
  старый набор JSON сохранён в архиве.
- Очереди подготовки и повторной отправки находятся в памяти и ограничены. При перезапуске
  или переполнении возможна потеря событий; outbox не используется.
- Независимый откат Redis к старой копии счётчиков не поддерживается: перед возобновлением записи
  нужно восстановить номера. При утрате ключа новый счётчик начинается после последнего бакета каталога.

Эти уточнения заменяют прежние описания fallback в последний бакет, последовательного чтения
бакетов и утверждение об отсутствии потерь. Целевые тесты запускаются через ./gradlew test.
